묘한운세 · 데이터 설계

사주 · 관상 · 타로를
한 스키마로 묶기

세 기능은 데이터 성격이 서로 다릅니다. 타로는 뽑기 기록, 사주는 생년월일에서 결정되는 계산, 관상은 사진에서 뽑아낸 측정값입니다. 공통 뼈대는 공유하고 다른 부분은 나누는 설계 — 다만 사주·관상을 저장하기로 정한 뒤에 꺼낼 문서입니다.

대상 luck_db · MariaDB 11 · utf8mb4 기준 origin/main + 타로 1차 구현 상태 스키마는 적용됨(sql/init/07~10) · 이관은 보류

현재지금은 타로만 데이터를 남깁니다

설계를 바꾸기 전에 무엇이 이미 있고 무엇이 없는지부터. 사주와 관상은 계산해서 화면에 뿌리고 끝나며, 회원 개념은 어느 기능에도 없습니다.

기능계산 위치저장채팅
사주 korean-saju · 서버 메모리 없음 없음
관상 MediaPipe · 브라우저 없음 무상태 매번 컨텍스트 재전송

타로만 앞서 있는 게 아니라, 타로가 세 기능이 공통으로 필요로 하는 것을 이미 한 번 풀어놨습니다 — 비회원 식별(guest_key), 결과 요약, 해석 출처(rule/llm), 대화 기록. 이걸 타로 전용으로 두지 말고 끌어올리는 것이 이 설계의 핵심입니다.

전제지금 적용할 설계는 아닙니다

이 문서는 목표 구조를 그린 것이지, 오늘 실행할 작업 지시가 아닙니다. 언제 값을 하는지 먼저 짚고 넘어갑니다.

업데이트 — 스키마는 미리 승격했고(sql/init/07~10), 이관만 보류 중입니다.

reading, chat_message, saju_chart, saju_reading, face_shape, face_reading 테이블은 이제 실제로 존재합니다. 로그인·저장 기능을 만들 때 맞춰볼 테이블이 미리 있는 편이 낫고, 전부 빈 테이블이라 ALTER TABLE로 고치는 비용이 거의 없어서 먼저 만들었습니다. 아래 논의는 기존 타로 데이터를 이 구조로 옮기는 이관에 대한 것이고, 그 결론은 그대로입니다 — 스키마가 있다고 이관까지 할 이유는 없습니다. 지금 앱 코드는 사주·관상 어느 쪽도 이 테이블에 쓰지 않고, 타로도 기존 tarot_reading을 그대로 씁니다.

공통 reading 뼈대는 사주나 관상 중 하나라도 결과를 저장하기 시작할 때 값을 합니다.

타로만 저장하는 동안에는 얻는 것이 없습니다. 테이블 하나를 둘로 쪼개고(reading + tarot_reading) 조인이 하나 늘 뿐입니다. 그런데 사주·관상을 저장할지는 아직 팀이 정한 적이 없습니다.

옛 구조로 계속 갈 때 실제로 막히는 것

하려는 일지금 구조로 가능한가
마이페이지 타로 기록그대로 가능 GET /api/tarot/readings 이미 있습니다
타로 채팅 저장동작 중 tarot_chat_message
마이너 아르카나 56장 추가가능 스키마 변경 없이 INSERT만
로그인 붙이기가능 tarot_reading.user_id가 이미 nullable
사주·관상 결과 저장비용 발생 기능마다 *_reading + *_chat_message를 따로
세 기능 통합 기록 목록비용 발생 세 번 조회해 코드에서 병합
관상 채팅 5회 제한을 서버가 강제불가 대화가 저장돼야 셀 수 있습니다

이관 비용은 실제로 큽니다

이 설계의 이행 스크립트를 실제 MariaDB에서 검증하다 함정 세 개를 밟았습니다. 검증 환경이라 잡았지, 운영 DB였으면 위험했습니다.

  • CHECK 제약이 FK와 충돌합니다. MariaDB는 ON DELETE SET NULL FK가 걸린 컬럼에 CHECK를 허용하지 않습니다(ERROR 1901). 기존 tarot_reading의 같은 CHECK가 통과했던 건 user_id에 FK가 없었기 때문입니다.
  • 트랜잭션이 DDL을 감싸지 못합니다. RENAME·CREATE가 암묵적 커밋을 일으켜, 중간에 실패하면 절반만 진행된 상태가 남습니다.
  • 롤백 스크립트가 두 번 돌면 데이터를 지웁니다. DROP TABLE IF EXISTS tarot_reading이 복구된 원본을 겨냥하게 됩니다. 상태를 확인하는 가드가 반드시 필요합니다.

권고 — 지금은 이관하지 않습니다. 옛 구조로 마이페이지까지 마치고, 사주나 관상을 실제로 저장해야 할 때 그 시점에 결정하는 편이 낫습니다. 그때는 무엇을 저장해야 하는지 이미 알고 있으니 판단 근거가 훨씬 분명합니다.

다만 이건 지금 해두면 좋습니다

어떤 답변이 LLM이고 어떤 게 규칙 기반인지 저장하지 않는 것은 지금 구조의 실질적 공백입니다. DeepSeek을 붙여놓고 나중에 답변 품질을 되짚을 방법이 없습니다. 이관 없이 한 줄로 됩니다.

ALTER TABLE tarot_chat_message
  ADD COLUMN source ENUM('rule','llm') NULL
  COMMENT 'assistant 답변을 무엇으로 만들었나';

결정네 가지 판단

각 항목마다 택하지 않은 대안을 같이 적었습니다. 뒤집을 근거가 있으면 그 자리에서 뒤집으면 됩니다.

공통 reading 한 장 + 기능별 상세 1:1

모든 결과는 reading 행 하나로 시작합니다. 소유자, 요약, 해석 출처, 상태, 시각처럼 세 기능이 똑같이 갖는 것만 여기 둡니다. 기능 고유 정보는 saju_reading · face_reading · tarot_reading이 같은 PK로 1:1로 물고 갑니다.

이렇게 하면 마이페이지의 "최근 본 운세"가 테이블 하나만 읽으면 됩니다. 기능이 늘어도 목록 쿼리는 그대로입니다. 채팅도 reading_id 하나로 붙어서 관상·사주 채팅이 공짜로 저장됩니다.

택하지 않은 것기능별로 완전히 분리된 *_reading 세 벌. 각 테이블은 단순해지지만 마이페이지가 세 번 조회해 코드에서 병합해야 하고, 채팅 테이블도 세 벌이 됩니다.

관상 사진은 저장하지 않습니다

얼굴 사진은 그 자체로 민감한 개인정보입니다. 지금 구조는 브라우저에서 MediaPipe로 측정하고 숫자만 서버로 보내면 되므로, 사진을 받지도 저장하지도 않는 선택이 가능합니다. face_reading에는 비율 다섯 개와 대칭 점수만 남습니다.

측정값만으로 결과를 다시 그릴 수 있어서 "다시 보기"도 됩니다. 사진이 필요해지는 순간(예: 결과 카드 이미지 저장) 별도 논의 대상이 되게 두는 편이 낫습니다.

택하지 않은 것사진을 오브젝트 스토리지에 두고 URL만 저장. 결과 재현과 개선에는 유리하지만, 보관 기간·삭제 요청·유출 대응이 전부 따라옵니다.

사주 계산 결과는 saju_chart로 공유합니다

사주는 같은 생년월일시·성별이면 언제 계산해도 같은 결과가 나옵니다. 리딩마다 사주 여덟 글자를 복사해 두는 대신, (생년월일, 시각, 시각모름, 성별, 엔진버전)을 유니크 키로 갖는 saju_chart에 한 번 계산해 두고 리딩이 참조합니다.

engine_version을 키에 넣은 이유는 korean-saju가 올라가 계산이 달라져도 과거 리딩이 그때 보여준 결과를 그대로 유지하기 위해서입니다. 새 버전은 새 행이 됩니다.

택하지 않은 것리딩마다 결과를 그대로 복사. 단순하지만 같은 사람이 열 번 보면 같은 여덟 글자가 열 벌 쌓이고, 해석 로직을 고쳤을 때 무엇이 언제 계산된 것인지 구분할 수 없습니다.

guest_key를 남기고 회원과 공존시킵니다

로그인 없이 바로 쓰는 흐름을 막지 않으려면 비회원 식별자가 계속 필요합니다. reading은 user_id와 guest_key를 둘 다 갖고, 둘 중 하나는 반드시 있어야 한다는 제약을 겁니다.

나중에 로그인이 붙으면 가입 시점에 그 브라우저의 guest_key를 가진 행을 user_id로 옮겨 붙이면 기록이 이어집니다. 열쇠가 브라우저에만 있다는 한계는 그대로이므로, 화면에서 그 사실을 정직하게 알려야 합니다.

택하지 않은 것로그인 필수. 데이터는 깨끗해지지만 첫 화면에서 이탈이 생깁니다.

구조테이블 관계

가운데 reading이 뼈대입니다. 세 기능의 상세가 같은 키로 1:1로 매달리고, 채팅은 기능을 가리지 않고 reading에 붙습니다.

명세테이블

각 항목을 펼치면 DDL과 그렇게 정한 이유가 나옵니다. 신규 는 새로 만드는 것, 유지 는 지금 그대로, 이관 은 기존 테이블에서 옮겨오는 것입니다.

계정 지금 없는 영역. 로그인이 붙을 때 필요합니다.
app_user회원 계정신규 
CREATE TABLE app_user (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  email         VARCHAR(190) NOT NULL,
  password_hash VARCHAR(255) NULL       -- 소셜 로그인만 쓰면 NULL
  nickname      VARCHAR(40)  NOT NULL,
  status        ENUM('active','dormant','withdrawn') NOT NULL DEFAULT 'active',
  created_at    TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at    TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_app_user_email (email)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

email을 190자로 자른 건 utf8mb4에서 인덱스 키 길이 한계(767바이트) 때문입니다. status에 withdrawn을 둔 이유는 탈퇴해도 리딩 기록을 바로 지우지 않고 익명화할 여지를 남기기 위해서입니다.

birth_profile사주에 쓰는 생년월일 프로필. 한 회원이 여러 개(본인·가족)를 가질 수 있습니다.신규 
CREATE TABLE birth_profile (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  user_id      BIGINT UNSIGNED NOT NULL,
  label        VARCHAR(40)  NOT NULL,   -- '내 사주', '엄마'
  birth_date   DATE         NOT NULL,
  birth_time   TIME         NULL,       -- 모르면 NULL
  calendar     ENUM('solar','lunar','lunar_leap') NOT NULL DEFAULT 'solar',
  gender       ENUM('female','male','unknown')    NOT NULL DEFAULT 'unknown',
  created_at   TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  KEY ix_birth_profile_user (user_id),
  CONSTRAINT fk_birth_profile_user FOREIGN KEY (user_id)
    REFERENCES app_user (id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

birth_time이 NULL인 것과 "자정에 태어남"은 다릅니다. 지금 코드는 시각을 모르면 정오로 대체하는데, 그 대체값이 아니라 모른다는 사실 자체를 저장해야 나중에 계산 방식을 바꿔도 원본이 남습니다. calendar는 음력 입력을 받을 계획이 있으면 지금 넣는 게 쌉니다.

공통 세 기능이 공유하는 뼈대.
reading모든 결과 한 건. 소유자·요약·상태를 갖습니다.이관 
CREATE TABLE reading (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  service       ENUM('saju','face','tarot') NOT NULL,
  user_id       BIGINT UNSIGNED NULL,
  guest_key     CHAR(36)        NULL,
  summary_title VARCHAR(120) NULL,
  summary_text  TEXT         NULL,
  interpretation_source ENUM('rule','llm') NOT NULL DEFAULT 'rule',
  llm_model     VARCHAR(64) NULL,
  status        ENUM('created','interpreted','failed') NOT NULL DEFAULT 'created',
  created_at    TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at    TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  KEY ix_reading_user  (user_id,   created_at),
  KEY ix_reading_guest (guest_key, created_at),
  CONSTRAINT fk_reading_user FOREIGN KEY (user_id)
    REFERENCES app_user (id) ON DELETE SET NULL,
  CONSTRAINT ck_reading_owner CHECK (user_id IS NOT NULL OR guest_key IS NOT NULL)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

인덱스 두 개가 마이페이지 쿼리를 그대로 받습니다 — WHERE guest_key = ? ORDER BY created_at DESC. service는 조건에 잘 안 들어가고 카디널리티도 3이라 따로 인덱스를 두지 않았습니다.

기존 tarot_reading의 소유자·요약·상태 칼럼이 전부 여기로 올라옵니다.

chat_message결과 화면 대화. 기능을 가리지 않습니다.이관 
CREATE TABLE chat_message (
  id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  reading_id BIGINT UNSIGNED NOT NULL,

tarot_chat_message에서 이름만 바뀐 것에 가깝지만, source가 새로 생깁니다. 지금은 답변 출처를 응답으로만 돌려주고 저장하지 않아서, 나중에 "LLM 답변 품질"을 되짚을 수 없습니다.

관상 채팅이 여기 붙으면 지금 매 요청마다 컨텍스트를 통째로 다시 보내는 구조가 사라집니다. 질문 5회 제한도 COUNT(*) WHERE role='user'로 서버가 셀 수 있어 클라이언트 상태에 기대지 않게 됩니다.

사주 계산은 결정론적. 결과를 공유합니다.

CREATE TABLE saju_chart (
  id             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  birth_date     DATE NOT NULL,
  birth_time     TIME NULL,
  time_unknown   TINYINT(1) NOT NULL DEFAULT 0,
  gender         ENUM('female','male','unknown') NOT NULL,
  engine_version VARCHAR(32) NOT NULL,   -- korean-saju 버전
  pillar_year    CHAR(2) NOT NULL,        -- 갑자 두 글자
  pillar_month   CHAR(2) NOT NULL,
  pillar_day     CHAR(2) NOT NULL,
  pillar_hour    CHAR(2) NULL,            -- 시각 모르면 NULL
  jeonggyeok     VARCHAR(40) NULL,
  yongsin        VARCHAR(40) NULL,
  sinsal         JSON NULL,
  computed_at    TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,

네 기둥을 한 문자열(str(saju))로 뭉쳐 넣지 않고 기둥별로 쪼갠 이유는, "월주가 무엇인 사람" 같은 조회나 통계가 나중에 반드시 나오기 때문입니다. 문자열로 넣으면 그때 파싱해야 합니다.

sinsal은 개수가 유동적인 목록이라 JSON으로 뒀습니다. 신살별 조회가 필요해지면 그때 saju_chart_sinsal로 펴면 됩니다 — 지금 미리 만들 근거는 없습니다.

앞의 셋은 validateFacePose()가 촬영 안내를 띄우는 품질 게이트일 뿐 결과 문구에 들어가지 않습니다. 다만 "측정은 통과했는데 결과가 이상하다"는 문의가 오면 이 값들이 있어야 재현됩니다. 개인정보 성격이 없는 순수 자세 지표라 넣어도 부담은 없으니, 넣을지는 팀 판단으로 남깁니다.

browEyeRatio는 측정만 하고 아무 데서도 읽지 않습니다 — 죽은 코드로 보입니다. 관상 담당자 확인이 필요합니다.

DECIMAL(5,4)은 0.0000~9.9999. 모든 비율이 얼굴 폭 대비라 1 근처에 모입니다. FLOAT 대신 쓴 건 판정 경계값(eyeRatio >= 0.205, jawRatio > 0.91)과 정확히 비교하기 위해서입니다.

칼럼명은 코드의 symmetryScore를 따랐습니다. 결과 문장을 만드는 함수 이름이 harmonyReading이라 헷갈리기 쉬운데, 값의 출처는 대칭 점수입니다.

detector_version은 saju_chart.engine_version과 같은 목적입니다 — 모델이 바뀌면 같은 사진도 다른 숫자가 나오므로, 과거 결과를 해석할 때 무엇으로 쟀는지 알아야 합니다.

이행기존 데이터를 옮기는 순서

타로가 이미 운영 중이라면 순서가 중요합니다. 각 단계가 끝난 시점에 서비스가 계속 동작해야 합니다. 앞의 전제 절에서 짚었듯 지금 실행할 작업은 아니고, 실제로 필요해졌을 때의 절차입니다.

  1. 새 테이블을 먼저 만듭니다app_user, birth_profile, reading, chat_message, saju_*, face_*. 아무도 안 쓰는 상태라 언제 해도 안전합니다.
  2. 기존 타로 리딩을 reading으로 복사합니다INSERT INTO reading (...) SELECT ... , 'tarot' FROM tarot_reading. 이때 id를 그대로 가져가면 아래 단계가 훨씬 쉬워집니다.
  3. 새 tarot_reading과 chat_message를 채웁니다기존 tarot_reading은 tarot_reading_old로 이름만 바꿔 남겨둡니다. 되돌릴 여지를 남기는 겁니다.
  4. 앱 코드를 새 테이블로 전환하고 배포합니다모델·서비스·라우터가 reading을 읽도록. 여기까지가 한 번의 배포입니다.
  5. 확인 후 옛 테이블을 지웁니다며칠 지켜보고 tarot_reading_old, tarot_chat_message를 DROP. 급할 이유가 없습니다.

이관 스크립트는 sql/init/에 두면 안 됩니다. install.sh가 그 폴더의 SQL을 매번 전부 실행하는데, 이관은 한 번만 돌아야 합니다. sql/migrate/에 두고 손으로 실행하며, 이관과 롤백 양쪽 모두 tarot_reading_old 존재 여부로 상태를 확인하는 가드가 있어야 두 번 돌려도 안전합니다.

앱 계정에는 DDL 권한이 없습니다. 1·3·5단계는 DB 서버에서 root로 실행해야 합니다. 스키마 파일은 이제 sql/init/07~10에 있어 install.sh가 자동으로 적용합니다. 이관·롤백 스크립트만 sql/migrate/에 따로 두어 손으로 실행합니다 — 이관은 한 번만 돌아야 하기 때문입니다.

확인정하고 가야 할 것

이 설계가 전제하고 있지만 아직 팀이 정하지 않은 것들입니다.

  • 로그인이 실제로 붙나요? 안 붙는다면 app_user·birth_profile은 만들 이유가 없고, reading.user_id도 지금처럼 놀리는 칼럼이 됩니다. 계획이 없다면 빼는 편이 정직합니다.
  • 사주·관상 결과를 정말 저장할 건가요? 지금은 화면에 뿌리고 끝납니다. 저장하는 이유는 마이페이지에서 다시 보기와 채팅 기록인데, 그 기능을 안 만들 거면 테이블도 필요 없습니다.
  • 관상 판정을 서버로 옮길 건가요? face_shape는 그 전제 위에 있습니다. 브라우저 판정을 유지한다면 이 테이블 없이 face_reading에 결과 문구를 직접 넣는 편이 단순합니다.
  • 관상 자세 지표(coverage · rollDegrees · noseOffset)를 남길까요? 결과에는 영향이 없지만 문의 대응 때 재현에 쓰입니다. 그리고 browEyeRatio는 측정만 하고 읽는 코드가 없어 죽은 코드로 보입니다 — 의도한 것인지 확인이 필요합니다.
  • 비회원 기록을 얼마나 보관하나요? guest_key 리딩은 주인이 브라우저를 지우면 영영 접근 불가인 채 계속 쌓입니다. 90일 정리 배치 같은 기준이 필요합니다.
  • SQLAlchemy ORM을 계속 쓰나요? 지금 DB를 쓰는 코드는 타로뿐이고 팀에 선례가 없습니다. 생쿼리로 간다면 이 설계는 그대로 두고 접근 코드만 달라집니다 — 스키마 설계와는 별개 문제입니다.

luck_db · MariaDB 11 · utf8mb4_unicode_ci — 이 문서는 제안이며 확정된 스키마가 아닙니다.
